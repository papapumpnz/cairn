# WP28 — Belief-aware planning and option induction

## Objective

Plan efficiently through learned theories and compress repeated successful behavior into verified options.

## Dependencies

WP18, WP27

## Owned scope

`cairn-plan`

## Inputs

Belief state, world theories, goals, action space, episode history.

## Deliverables

Deterministic A*, contingent AO*, bounded MCTS, plan certificates, option theories, and planner selection policy.

## Required design

Use symbolic state hashes and admissible domain-independent heuristics where available. When theory posterior is concentrated, use deterministic planning. When observations can resolve theories, build a bounded belief tree. Use MCTS only for large/stochastic spaces, with exact model rollout where possible. Mine repeated action-event segments into initiation, policy, termination, expected-effect, and failure clauses; verify on distinct contexts.

## Public API obligations

`Planner` trait, `AStarPlanner`, `AOPlanner`, `MctsPlanner`, `PlanResult`, `OptionTheory`, `OptionInducer`, and planner metrics.

## Test plan

Shortest path, contingent door/key, hidden dynamics requiring experiment, sparse reward, option false initiation, changed layout, planner timeout, deterministic tie breaks.

## Acceptance criteria

I2 gates; options reduce expansions at least 5 times on held-out layouts; deterministic planner returns optimal path on exhaustive small worlds; ordinary action decision below 500 ms where plan depth permits; plan replay exact.

## Forbidden shortcuts

Do not store raw action sequences as skills. Do not use game-specific heuristic code.

## Mandatory operating constraints

- CPU-only and transformer-free. Run `cairn-check` before handoff.
- No ARC task IDs, full-grid hashes, memorized outputs, or task-family branches in production code.
- Deterministic semantic output for fixed input, semantics version, seed, and work budget.
- Canonical serialization for every persistent public type.
- Exact errors: distinguish invalid input, unsupported semantics, capacity cap, timeout, and internal defect.
- Add metrics before optimizing. A speed claim requires the naive or previous baseline on the same machine.
- No evaluation split access.

## Required handoff

Return a committed implementation, public API documentation, test commands, benchmark commands, evidence artifacts, acceptance-criterion table, known limitations, and the exact downstream interface tag.
